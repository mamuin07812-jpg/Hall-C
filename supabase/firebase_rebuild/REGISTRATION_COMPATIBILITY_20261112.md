## Name-column mapping decision and correction

The user confirmed that the fourth student field means **great-grandfather's name**, not family name. The four student fields map to `first_name`, `father_name`, `grandfather_name`, and `great_grandfather_name`. The teacher's single full-name field remains `p_name`. The final registration RPC now rejects any blank/whitespace-only student name component server-side; the native HTTP suite checks each of the four omissions and verifies rejection happens before the OTP `jti` is consumed.

The candidate SQL registration inserts in migrations 001, 003, 004, and 005 previously copied `p_great_grandfather_name` into both `profiles.great_grandfather_name` and `profiles.family_name`. This was incorrect because the schema and `update_own_profile` treat `family_name` as a separate field. The candidate migrations have now been corrected: registration writes only `great_grandfather_name`; `family_name` remains unset until separately provided. No migration has been applied to any database.

## Gaps blocking a real application link

1. Current Flutter registration and setup contain no Supabase RPC call, Supabase JWT exchange, or roster import path; registration remains Firebase Auth + Firestore.
2. The user-confirmed student UI supplies four name components, matching the SQL RPC. However, GitHub main/PR snapshots show one shared full-name field, but the prior local-project capture confirms four student controllers and one teacher full-name controller. The capture shows legacy duplication into `familyName`; do not carry that duplication forward. The approved roster separately supplies canonical `full_name`, so precedence between roster display name and the four entered components must be documented.
3. No Admin feature imports the approved roster. Without enabled `university_id` + normalized email rows, SQL student signup cannot succeed.
4. Current Firebase email-link verification is not the staged Worker OTP proof. Migration 005 requires purpose/UID/email-bound proof claims and atomically consumes their `jti`.
5. The actual signup completion step in `register_page.dart` collects gender, stage, and hall, matching the SQL completion RPC inputs. The separate `account_gate.dart` setup/profile path is not equivalent and has no RPC call; it must be reconciled deliberately if it remains reachable for incomplete accounts. Stage and hall must match the approved roster.
6. Teacher specialization is free text in the UI but restricted to a fixed SQL allow-list; the app-side values and server validation need an agreed contract.
7. Teacher specialization compatibility: the app field is free text. Migration 005 canonicalizes the known Arabic and English aliases for the 10 established subjects and rejects unknown strings before consuming OTP proof. Native PostgREST tests passed for Arabic normalization and unknown-value rejection.
8. Student academic completion was validated over native PostgREST: roster-matched gender/stage/hall succeeds (void RPC returns HTTP 204); mismatched stage, mismatched hall, and unsupported gender are rejected without marking the profile complete. The actual signup form's gender/stage/hall fields map to this RPC. 9. Added an offline seven-column roster CSV template and validator; it checks schema, duplicate IDs/emails, email shape, stage, hall, enabled boolean, quoting, and 5,000-row limit without printing student values or uploading data. 23 static/CSV tests and 23 native PostgreSQL/PostgREST checks passed in GitHub Actions run 43218575411.
10. The name semantics are resolved: `great_grandfather_name` is the fourth student name component; `family_name` is separate. The prior local-project capture confirms the four student fields but shows legacy Firestore duplication into `familyName`. Candidate SQL mappings keep the fields separate. The final RPC also enforces all four names as required, with native HTTP regression coverage passing in GitHub Actions run 43216763874 (15/15 static tests and 17/17 native PostgreSQL/PostgREST checks).

The contract tests in `registration_contract.test.mjs` pin the current app-side writes and SQL signatures/requirements, including these deliberate mismatches. Their purpose is to expose contract drift, not to claim application integration.
