Scope: read-only comparison of the current Flutter/Admin registration flow with the staged Schoolivia Supabase contracts in migrations 001–005. No Flutter, Admin, Firebase, or SQL migration code was changed during this review.

## Name-column duplication review

Migrations 003, 004, and 005 each insert the same `p_great_grandfather_name` value into both `profiles.great_grandfather_name` and `profiles.family_name`. The baseline registration in migration 001 has the same overlap. However, `update_own_profile` has a distinct `p_family_name` parameter and composes `full_name` using that field separately from the four registration name components. The schema therefore treats family name and great-grandfather name as separate concepts. The current Flutter registration only supplies one undifferentiated full name and offers no evidence for how a value should be split. This review flags the duplicate as an unresolved modeling/data-mapping issue and intentionally does not change it.

## Gaps blocking a real application link

1. Current Flutter registration and setup contain no Supabase RPC call, Supabase JWT exchange, or roster import path; registration remains Firebase Auth + Firestore.
2. The student UI supplies one full name, while the SQL RPC requires four name components. The approved roster separately supplies the canonical `full_name`; mapping/name precedence must be decided.
3. No Admin feature imports the approved roster. Without enabled `university_id` + normalized email rows, SQL student signup cannot succeed.
4. Current Firebase email-link verification is not the staged Worker OTP proof. Migration 005 requires purpose/UID/email-bound proof claims and atomically consumes their `jti`.
5. Student setup has no gender input, while the SQL completion RPC requires one. Stage and group must also match the roster; the current Firestore/Admin edits can diverge from it.
6. Teacher specialization is free text in the UI but restricted to a fixed SQL allow-list; the app-side values and server validation need an agreed contract.
7. `great_grandfather_name` and `family_name` are separate schema concepts but currently receive one input. Resolve intended semantics before any migration or data conversion.

The contract tests in `registration_contract.test.mjs` pin the current app-side writes and SQL signatures/requirements, including these deliberate mismatches. Their purpose is to expose contract drift, not to claim application integration.
